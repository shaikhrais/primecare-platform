# Growth presentation ownership, 2026-11-07

## Actual route and authority

`main.ts` dispatches the already registered `/growth` route to `growth/dashboard.ts`. The prior entry-only manager call did not own the renderer's asynchronous list load or its retained child controls. An actual-module baseline reproduced a private read after registration removal, a late read overwriting a replacement root, and a retained finance form issuing a write after root replacement.

This change owns that existing renderer and its existing children: leads/campaigns/plan, tasks and task actions, contacts/duplicates/search, briefs/reviews/capacity, business onboarding/handoffs/finance, operations/team/calls/appointments, intake links/QR, performance/email/delivery review, and marketing statements/PDF. It does not create a screen, route, endpoint, permission, label, or governance record. Existing transport endpoint, request bodies, actor token, tenant authority, capability gates, version fields, and idempotency keys are retained. Server services remain the only authorization and persistence authority. Presentation registration is not a grant.

## Ownership and recovery

The renderer verifies the existing four manager connections before reads, presentation, and each retained control. It retires on root replacement/removal, session change, path/query change, full renderer replacement, manager failure, and non-persisted pagehide. Hash-only section navigation remains supported. Current 401 clears the session; stale 401/403 cannot sign out or redraw a newer owner. Current 403 revokes visible authority. Storage and navigation exceptions produce the existing contained configuration error.

Bindings are guarded before payload extraction, including forms that read nested rows before calling mutate. A pending refresh blocks controls from acting on old records. Each render gets a separate lease; report setters and exports recheck it after asynchronous work. PDF URLs and revocation timers are cleaned on owner retirement. Actual shell binding is part of the owner commit. The existing appearance dialog receives an optional ownership callback, including its native change listeners, asynchronous theme/library writes, and imports. Close/cancel invalidates pending import revisions. Existing shell consumers do not opt into the new callback automatically.

JSON collections and nested data consumed by growth rendering are validated before presentation. Malformed reads fail closed instead of reusing a stale authority snapshot. No optimistic rows are added from write acknowledgements. Accepted writes use GET-only recovery until the current scoped server snapshot proves reflection. Version reflection requires positive safe integers and a response version newer than the submitted baseline (a zero baseline is allowed only where existing creation/default contracts use it). Creation reflection requires a new matching response ID, with versions where the server supplies them. Finance and handoff creation use their existing ID-only response contract. Calls require a new call ID and matching lead-version advance. A missing row in a paginated snapshot is not proof.

Uncertain writes keep the original body and existing idempotency key for retry. Delivery resolution does not reset an email retry key while an uncertain email receipt exists; that retry must retrieve the original terminal state before a fresh confirmed send. For all uncertain commands, changed retained input values cannot silently change the retry. Accepted and uncertain receipt fields stay locked until safe reflection. Ordinary same-owner language/report redraw draft preservation remains. Fail-closed session/route/configuration or malformed-read retirement can lose unsubmitted drafts. Accepted command input evidence is held in memory while this owner can recover.

## Explicit conservative boundaries

- The existing performance email acknowledgement has terminal provider state but no correlatable delivery ID/request hash. An accepted/not_sent receipt stays GET-only through failed, malformed, or wrong-scope refresh. After a valid same-scope snapshot is presented, the original acknowledgement is shown using the existing “Email accepted by provider” or “Confirmed not sent” resource. This is not delivery success or delivery-row reflection. A newly rendered blank email form with an unchecked confirmation allows a later intentional send; retained old forms remain inert.
- Duplicate review reflection is not provable from the paginated read. Its accepted control stays GET-only for the life of this owner, including after disappearance of a duplicate pair. This intentionally limits a later deliberate review from the same retained form. It is not full repeated-review workflow preservation.
- Receipt protection and draft storage are owner-local and non-durable. Full renderer replacement, navigation, or reload discards them. No durable exactly-once guarantee, cross-owner retry guarantee, or server cancellation is claimed. The server's existing idempotency and authority remain necessary.
- BFCache checks use controlled event/DOM/network models. They show deferred effects until valid modeled resume, not browser BFCache acceptance.
- Browser automation was not rerun after the earlier sandbox launch failures. These are actual TypeScript modules exercised with controlled DOM/network fixtures, including an independent real-shell harness. They do not prove visual layout, keyboard/screen-reader acceptance, production connectivity, or deployment readiness.
