# Coordinator database-demo screen ownership

## Bounded change

This extension of the preserved Screen Management candidate integrates the existing non-personal `/psw?dataset=demo` and `/care?dataset=demo` dispatcher, presentation and actions with `care/ownership.ts`. The predecessor deliberately disposed its route owner before rendering this branch. No route, permission, registry record, API, service action, production database data or release grant is added. This is an authenticated, saved synthetic training workspace, not production clinical care.

The route owner guards current root identity, URL/query, session, charge context, manager registration and presentation services. Existing body dialogs have child ownership, Close/Cancel/removal cleanup, and guarded callback properties, including dynamically inserted waitlist choices and drag/drop proposals. Local navigation retires old dialogs. Detached controls cannot write, export, print or navigate. Download URLs, timers and observers are released on disposal. Synchronous replacement during dialog acquisition cleans up the orphan without touching the replacement root.

All 19 existing mutation families retain their action names and payloads. The inherited transport still supplies bearer authentication, tenant query, additional-charge header and idempotency key. `canManage` is server metadata; the synthetic practice selector never grants management. A valid response changing actor, tenant, role or management scope retires the old view and its dialogs without signing out. Only a current 401 can sign out the current session; a current 403 retires denied controls. Late errors never revoke a replacement session or owner.

## Writes, retries and response integrity

- A dispatched write locks ordinary controls and editable fields, while Close and Cancel stay usable. Closing a dialog cannot cancel a POST already sent to the server. Its late continuation is suppressed.
- Existing handlers prepare command values locally, but candidate rows are not rendered as saved. Failed submissions preserve the same dialog and draft. Record-based callbacks re-find the current saved record after rollback.
- An unchanged uncertain retry retains the complete original body and idempotency key, including generated identifiers and timestamps. Retry identity includes the dialog's semantic visit, request, incident or provider/date context and synthetic practice mode. Identical text on a different record does not replay the earlier command. A changed draft is a new command. An accepted and successfully rendered snapshot retires completed attempts so a later intentional creation is new.
- Accepted acknowledgements are retained within the same route owner until a valid scoped snapshot has actually rendered. The acknowledgement must have a positive safe-integer version strictly newer than the submitted version. A subsequent confirming snapshot must be at least that version. A failed or malformed acknowledgement/read cannot authorize another POST. Ordinary same-owner recovery uses GET rather than repeating an accepted mutation, including after closing/reopening a dialog.
- Validation covers the response envelope and nested presentation dependencies across inactive pages, including provider/client references, visits, waitlist, incidents, messages, availability, feedback and audit. A malformed inactive page cannot silently release a receipt merely because the schedule happened to render.
- A successful explicit refresh replaces the saved view and retires its old dialogs. A failed or malformed refresh preserves an open draft. A valid scope change deliberately retires the entire old view and loses its draft rather than exposing controls under changed authority. An acknowledgement with missing/invalid scope or version cannot be safely correlated for automatic release; it remains blocked for this owner. There is no durable receipt/draft guarantee across reload, new owners or sessions.

BFCache tests use a controlled model: publication waits while suspended, then revalidates on persisted pageshow. They do not establish browser BFCache implementation behavior or server cancellation.
