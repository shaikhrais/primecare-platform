# Care delivery: RN, supervisor and support worker

This is the first working routine support-care bundle. The `/care` workspace connects existing tenant accounts, provider profiles, clients and visits through the governance API. It is implemented and locally tested; production release and independent clinical, privacy and accessibility acceptance remain pending. No real employees, credentials, patients or assignments were created during development.

## Duties and app steps

| Step | Responsible role | Work in the app | Evidence / next gate |
| --- | --- | --- | --- |
| 1 | Clinical director or qualified RN field supervisor | Select an existing employee; record independent credential, employment, induction and competence verification. Create/approve a missing provider profile in the same form. | Dated, role-bound clearance with expiry and human verification reference. No self-verification. |
| 2 | Scheduler, tenant admin, clinical director or RN field supervisor | Select an existing visit and assign a nurse, independent clinical supervisor and support worker. | Three distinct, currently eligible people in the same tenant. |
| 3 | Assigned RN or RPN | Write assessment, precautions, escalation instructions, consent evidence, plan validity and individual support activities; save and submit. | Current qualification, explicit consent and competence confirmation; maximum 20 activities and 30-day plan validity. |
| 4 | Assigned RN field supervisor or clinical director | Review independently; approve or return the plan with a note. | Author cannot approve their own plan. Returned plans require correction and another review. |
| 5 | Assigned PSW or HSW | Read the approved instructions, acknowledge the assignment, confirm current consent and start at the permitted time. | Server rechecks plan, team eligibility and visit assignment; captures clearance versions. |
| 6 | Assigned PSW or HSW | Record each activity as done, refused, not done or concern, with factual notes; report concerns and submit the visit. | Every activity needs an outcome. Refusal is recorded, never converted into completion. |
| 7 | Assigned nurse / clinical supervisor | Document follow-up against each open concern. | Unresolved concerns block final review. The in-app queue is not an emergency notification service. |
| 8 | Assigned independent clinical supervisor | Review the submitted record and complete review. | The actual visit becomes completed; the original outcomes and refusals remain visible. This does not approve payroll. |
| 9 | Authorized assigned care staff / operations | Add signed corrections, or cancel/reassign a pre-start assignment. | Corrections append; historical entries cannot be edited or deleted. Reassignment clears plan approval and removes the previous worker's access. |
| 10 | Assigned PSW / HSW | Before care starts, report inability to attend, no access, client unavailability or missing current consent. | Care is blocked in `coverage_needed`; scheduling sees the reason category and timestamp, without the worker's clinical/free-text note. |
| 11 | Scheduling team | Open the coverage filter, contact the appropriate people using organization procedures, then reassign or cancel with evidence. | A replacement requires a fresh nurse plan and independent approval. Reassignment removes the prior worker's chart access. |
| 12 | Assigned independent supervisor | Return a submitted visit record with a specific correction request. | State becomes `correction_requested`; no new physical care or task outcomes are permitted in this state. |
| 13 | Assigned support worker | Read the correction request, add a signed factual addendum, then resubmit. | An addendum by that worker after the latest return is mandatory. Original outcomes remain intact. Repeated returns require new addenda. |
| 14 | Every authorized role | Use all, my tasks, past-target, concerns and coverage filters to identify the next responsible person/team and follow up. | Filtering runs on the server before pagination. These queues are scoped to authorized tenant/assignment records. |
| 15 | Care employee or scheduling operations | Record explicit UTC availability with scheduling evidence. | A support worker needs one active window covering the whole visit before assignment/start. Availability does not establish clinical qualification. |
| 16 | Care employee / operations on their behalf | Request time off. | Pending requests require an independent decision and do not silently cancel visits. |
| 17 | Scheduling / clinical operations | Approve or decline another employee's request; record agreed changes to approved leave. | Self-approval denied. Decisions are versioned and append to immutable history. Approved leave blocks affected team assignments. |
| 18 | Employee / operations | Withdraw an availability window or pending request with a note. | Affected pre-start cases appear in the coverage queue; signed care records remain intact. |
| 19 | Scheduling / clinical operations | Select a source visit, local first date, time zone, duration, weekly interval and count; preview. | Preview shows client, service, address, skills and every local/UTC occurrence. |
| 20 | Same operator | Confirm the client agreement and create the previewed visits. | Exact preview must be less than 15 minutes old with unchanged source data. All visits are created atomically, unassigned and without copied clinical plans. |
| 21 | Scheduling / clinical operations | Reschedule a pre-start care assignment with client agreement and evidence. | Client/staff conflicts roll back changes. Success clears plan, clinical approval and worker acknowledgement. |
| 22 | Scheduling / clinical operations | Cancel an unassigned future series occurrence with evidence. | Stale changes and assigned occurrences are rejected; other dates remain unchanged. |
| 23 | Assigned PSW / HSW | After submitting the visit record, attest actual work start/end, breaks and supporting notes. | Raw timestamps, net reported minutes and the electronic care-start comparison remain available for review. |
| 24 | Another operations person | Verify time evidence or return it with a correction request. | No self-approval. Time verification is separate from clinical review and never releases payment. |
| 25 | Assigned worker / independent reviewer | Submit corrected time after a return; repeat review. | Original submissions and approvals remain in immutable history. Previously approved time can only be reopened by an independent operations decision. |
| 26 | Scheduling / clinical operations | Cancel the actual client appointment before care starts, with explicit agreement/evidence. | Both appointment and assignment become cancelled. Staff reassignment cannot restart that cancelled source visit. |

The clinical director has organizational verification responsibilities. RN field supervisors require their own current qualification before verifying others. Scheduling permission alone provides no access to assessment, plan or clinical notes. Owners, marketing staff and platform administrators receive no clinical chart access from this module. RN and RPN accounts can author assigned plans; supervisory approval is restricted to the assigned clinical supervisor role.

## Boundaries and exceptions

- Routine activity categories are personal support, mobility support, meal support, household support, companionship and observation/reporting. Medication administration and controlled-act delegation are outside this bundle. Free-text instructions still require professional review; the software does not clinically validate their content.
- Creating an account or assigning an RN/PSW role does not verify registration or establish competence. A human must verify applicable registration, employment, induction, training and the suitability of the actual assignment. References are manually recorded; there is no live CNO registry integration.
- Accounts must already exist and be active. Client accounts and a source visit must exist before recurring visits can be created. Provider-profile onboarding is available through the verifier form/API, but cannot bypass a retraining lock. An authorized training-release workflow remains separate.
- Expired/revoked clearance, an expired plan or an invalid team blocks new care and a “done” outcome. An already assigned worker may still record factual non-performance, concerns and the visit record. An eligible independent supervisor may review historical work using its original start evidence without reinstating the worker.
- Cancellation is available before care starts. A cancelled case can be reassigned with a fresh plan when the underlying visit is still active. Cancelled or rejected source visits are never silently completed by a clinical review.
- New concerns remain in the worklist even after completion. Follow the organization's emergency and escalation procedures outside the app when immediate response is required; there are no automatic emergency calls, messages or escalation timers here.
- “Completed” means the submitted visit record was reviewed. It does not mean every activity was performed, authorize payment, calculate wages, or establish company-wide employee performance policy.

## Screens, API and data

One governed care workspace presents role-specific summaries, clearance/profile onboarding, assignment, plan writing, independent review, activity outcomes, concern follow-up, corrections, coverage exceptions and immutable history. RN/support roles land directly in this workspace. The account/workspace link provides access to account navigation and logout. English, French and Spanish are included. The [numbered task and functionality checklist](TASK_CHECKLIST.md) identifies implemented duties and remaining release dependencies.

The personal queue also includes missing/returned worker time records and independent time reviews. The task queue derives responsibility from persisted workflow state: nurse preparation, independent supervisor plan review, worker acknowledgement/start/documentation, supervisor visit review, worker correction, or the scheduling team's coverage resolution. Open concerns independently identify the assigned nurse and supervisor for follow-up, including concerns raised after a record was reviewed.

Operational timing defaults are preparation/acknowledgement/start by scheduled start, documentation by scheduled end plus two hours, review within 24 hours of submission, and corrections within 24 hours of the latest return. Coverage needs attention when reported. These are governed operational targets, not clinical triage rules, a claim about hours actually worked or automatic findings of misconduct. New notes do not reset a correction deadline; a resubmission starts a new review deadline. Changes to these defaults require governed policy registration; no tenant self-service timing editor is included.

All database transactions run through the server API; browser bundles contain no database driver. The server checks the active session, tenant, current role, assignment, clearance, state and optimistic version. Clients cannot override tenant scope. Mutations use idempotency keys; access and signed actions are audited. Reusing an earlier successful request does not bypass current eligibility.

| Endpoint | Purpose |
| --- | --- |
| `GET /v1/governance/care` | Scoped worklist, capabilities, authorized roster and optional case detail |
| `POST /v1/governance/care/clearances` | Append independent human verification; optionally create/approve provider profile |
| `POST /v1/governance/care/cases` | Assign an existing visit |
| `POST /v1/governance/care/cases/{id}/actions` | Versioned plans, review, consent/start, outcomes, concerns, follow-up, reassignment, rescheduling and corrections |
| `POST /v1/governance/care/staffing` | Availability and independently decided time-off requests |
| `POST /v1/governance/care/schedules` | Preview/create recurring visits and cancel unassigned future occurrences |
| `POST /v1/governance/care/time-records` | Worker-attested time and independent, versioned review |
| `POST /v1/governance/care/handovers` | Private, independently reviewed same-client shift handovers and receiving-team receipts |
| `POST /v1/governance/care/followups` | Owned operational tasks, blockers, evidence and independent source-backed verification |

Contracts and error responses are in [openapi.json](openapi.json). The policy, translations, component mappings and grants originate in the governance database through `scripts/register-care-governance.py`; exports are reproducible. Apply `packages/database/migrations/20261017_care_delivery.sql`, then `20261018_care_task_workflows.sql`, then `20261019_care_staffing.sql`, then `20261020_care_schedules_time.sql`, then `20261021_care_handover_followups.sql`, then `20261022_care_task_deadline_requests.sql`, then `20261023_care_task_workload.sql`, then `20261024_care_task_dependencies.sql`. They add clearances, cases, immutable events, request deduplication, rate counters and access logs, while linking the existing users, tenants, visits and provider profiles. The second migration extends existing state constraints and indexes exception/correction event deadlines without rewriting historical entries. The third adds staffing windows and immutable decision events; the fourth adds schedule previews/series and reported-time review records with immutable events. The fifth adds handovers, receiving-team receipts and operational follow-ups with immutable evidence. The sixth adds pending deadline-request fields and consistency constraints without changing existing deadlines. The seventh adds an index for unfinished employee-task workload; it does not create tasks or alter history. The eighth adds immutable same-case prerequisite links and independent release records, with composite foreign keys and supporting indexes.

Worklists paginate 25 cases; staffing records independently paginate 25 entries with staff filtering before pagination. The roster is bounded at 200 people with a truncation indicator, unassigned visits at 100 and individual case history at 1,000 events. Large-organization roster/visit search and extended history pagination remain future work. Unsaved clinical drafts stay in memory, not browser persistent storage. The authentication token uses the existing session-storage mechanism. Stale case responses cannot replace a newer selected case.

## Staffing controls

The availability/time-off section uses `POST /v1/governance/care/staffing` and the scoped care snapshot. A care employee sees their own records. Operations can record on behalf of care employees, filter authorized staff and decide another employee's leave request. Records include the request and every later decision. No diagnosis or medical explanation is required; the form requests scheduling facts only. Personal leave notes are not returned to other care team members through a clinical case.

Windows use explicit UTC instants, last at most 31 days, may start up to 31 days in the past and end up to 365 days ahead. One availability window must cover a visit; adjacent declarations are not automatically merged. Availability windows do not recur automatically; recurring client visits use the separate scheduling workflow below. A pending leave request can be withdrawn; approved leave requires an operations decision with evidence to revoke. Self-approval is denied even for employees with an operations role. This records scheduling decisions, not statutory leave entitlement or payroll policy.

Creation/reassignment rejects support-worker overlaps across active source visits, including visits without a care case. A visit ending exactly when another begins is permitted. Nurses and supervisors may oversee concurrent support visits; approved leave for any assigned team member still blocks assignment/start. Missing/invalid visit timing requires coordinator correction. Travel time, actual visit overruns and maximum-hours calculations are outside these checks.

Assignment, reassignment, visit start, care-module clearance changes and staffing changes coordinate through tenant/staff advisory locks. Qualifications and staffing are rechecked in transactions. Staffing changes never silently complete or cancel a visit, or erase signed records. Affected pre-start cases appear in coverage and scheduling's work queue. Already-started workers retain factual documentation access when availability later changes.

Migration creates no fabricated availability for existing assignments. Their warnings must be resolved before a new start. These checks protect the care API operations; separate integrations that change source visit assignments/timing must adopt the same guard and lock protocol for a system-wide reservation guarantee. Visit start rechecks the latest source schedule as an additional gate.

## Recurring visits and schedule changes

Operations can preview and create up to 12 weekly visits, at one-to-four-week intervals, within 90 days. Each duration is 15–720 minutes. Supported time zones are America/Toronto and UTC. Weekly schedules preserve the local wall time through daylight-saving changes. A repeated or nonexistent local time is rejected; the operator must select a valid local time or explicitly use UTC. Preview is mandatory, belongs to the creating operator, expires after 15 minutes, and becomes stale when the source visit changes. Creation rechecks active client/service and conflicts even after preview.

Creation copies only the existing client/service, required skills and visit address/location. It does not copy clinical notes, plan approval, worker assignment, billing/booking links, rates or completed-care status. No staff are automatically selected. Each occurrence needs the normal eligibility/availability checks, assignment, nurse plan, independent approval and consent. Source visits must have an active same-tenant service and recorded required skills; missing setup is rejected rather than invented. The source dropdown shows the first 100 eligible visit templates.

A tenant/client lock serializes competing schedule batches. A client overlap blocks the entire batch; failed validation or audit writes leave no partial series. Series and their visit mapping are immutable. The series list is paginated at 25 and shows actual source-visit status. Operations can cancel an unassigned future occurrence using its current update timestamp. Once assigned, use “Cancel client appointment” on the care record to cancel the actual appointment. This requires explicit confirmation/evidence and cannot be used after care starts. The separate “Cancel care assignment” action leaves the source appointment active so replacement coverage can be arranged. A cancelled source appointment cannot be restarted through reassignment.

Pre-start rescheduling requires explicit client agreement, a signed note, future UTC start and duration. It rechecks client overlap, staff eligibility, availability and approved leave within the transaction. Success returns the case to awaiting a new nurse plan and clears clinical approval/worker acknowledgement. It cannot reschedule already-started care. The old schedule and evidence remain in signed event history. This is a bounded series creator, not an indefinitely running recurrence job or bulk series editor.

## Reported work time

For started support visits whose care record has been submitted, the assigned PSW/HSW can submit actual start/end, break minutes and explicit personal attestation. Current clinical clearance is not required to document historical work. The account must remain active in an authorized support role. This does not cover unstarted/cancelled attendance, travel, nursing administration or all employee timesheets.

Reported times must be in the past, within the last 366 days, with a positive interval of at most 24 hours and breaks below the elapsed interval. Net displayed minutes are whole elapsed minutes minus reported breaks; raw timestamps remain in history. This display is not a payroll rounding rule. A reported start differing from the electronic care-start timestamp by over 15 minutes is highlighted, not automatically rejected. Electronic start is application evidence, not GPS proof of presence, and there is no automatic electronic checkout.

Operations can verify another worker's record or return it for correction. Approval requires explicit evidence-review confirmation and records the contemporaneous clinical status. Clinical review and time verification are separate; one does not silently approve the other. Returned records can be resubmitted only by the assigned worker. Independent operations can reopen previously verified time with evidence; the old approval remains visible. Version checks, a case lock and immutable events prevent silent overwrites. Each report supports up to 50 signed versions; the report becomes read-only at that bound.

Employment notes and time history are visible to the assigned worker and authorized operations, not to unrelated clinicians, clients or marketing roles. A 25-record time-review list and the personal task queue expose pending and returned work. No time-review deadline, wage rate, pay eligibility, deduction, tax, statutory entitlement or payment is calculated. No payroll export or transmission occurs in this bundle.

## Private shift handovers

Assigned source care staff can prepare a factual handover after their visit starts, for a later, distinct, pre-start visit belonging to the same client and tenant. The source author needs an approved provider profile; expired clearance does not prevent factual historical documentation. An independent currently eligible source nurse or supervisor must approve, return or withdraw it. The author cannot review their own handover. Returned or approved text can be revised by its original author only before receiving care starts; revision requires another independent review.

Pending clinical text is visible only to the authorized source clinical team. Receiving clinicians see approved content; scheduling and tenant operations see metadata and status only. Approval resets a previously approved/accepted receiving plan to draft, preserving the plan and prior signed evidence. The current receiving nurse or supervisor must acknowledge every approved incoming handover before plan approval; the current receiving support worker must acknowledge before starting. Pending or returned handovers block those gates. Receipts bind the handover version, receiving team and schedule revision, so reassignment or rescheduling requires fresh acknowledgements even when the same person returns. Old versions and receipts remain immutable.

The inbox paginates 25 records using `handoverOffset`. Each case supports at most 10 incoming/outgoing handovers and each handover at most 20 signed content versions; final review/withdrawal capacity is reserved at the bound. The receiving-visit picker is limited to 100 eligible later cases. Handovers are factual care communications, not treatment orders or emergency notifications. They cannot be changed after receiving care starts.

## Accountable operational follow-ups

Operations can assign a care-record-linked task to an active same-tenant care-team member or operational employee. A task has a category, named owner, due date within 30 days and operational instructions. The owner can start work, report blockers and submit evidence. Another authorized operations person must verify or return it; no self-verification is allowed. Operations may reassign or cancel with signed evidence. Reassignment resets the task to open and preserves the previous owner, deadline and history.

Verification checks actual source state for coverage, plan review, visit review, documentation, staff clearance, time review and handover review. A completion claim alone is insufficient. Other operational work requires explicit independent evidence review and is labelled as a manual review, rather than claiming an automatically checked source outcome. Verification captures the contemporaneous case version/state; subsequent changes do not retrospectively turn that verified work into employee failure. Owners who lose care assignment can still report blockers or submit evidence on their own operational task, but regain no access to the care chart.

The separate follow-up panel offers all/mine/late/review/deadline-request filters, open/late/review/pending-deadline counts and 25-record pages, using `followupView` and `followupOffset`. These queues are separate from the visit-stage queue. Each task supports 50 signed versions, reserving capacity for a final submission and independent decision/cancellation. Completed/cancelled tasks are read-only. Instructions and evidence must contain operational facts, not medical notes; free-text content still requires organizational privacy supervision. There are no automatic reminders, employee disciplinary findings, wage calculations or payment decisions. Late tasks require a human to examine blockers, workload and evidence.

## Operational deadline requests

The task owner can request a later deadline with operational evidence. The proposed UTC instant must be later than the current deadline, in the future and no more than 30 days ahead. Only one request may be pending. The current deadline and late flag still apply until an independent operations person approves. The request does not complete work or change its open, blocked, in-progress or submitted status. Current authorized owners retain this operational workflow even after losing care-chart access.

Another operations person can approve with explicit evidence-review confirmation or decline with a reason; an operations employee cannot decide their own request or reassign their own task to bypass independent deadline review. Another operations person must perform that reassignment. Decisions preserve work status and sign the previous deadline, proposed deadline, requester, request time and effective deadline. Expired proposed deadlines cannot be approved; withdraw or decline the request before proposing a new future time. Owners may withdraw an unnecessary request. Reassignment, cancellation and independent completion verification close pending requests in the same transaction, recording the closed request in immutable history. A failed audit write rolls back the deadline and decision. Existing idempotency and current-authorization checks apply.

In the follow-up panel, owners enter the requested UTC deadline and reason. Operations select the deadline-request filter (`followupView=extensions`), read the evidence and choose approve or decline. Counts and filtering run on the API before 25-record pagination. The deadline/ownership history exposes original, requested and effective values, including request closure. This does not change clinical-plan deadlines, appointment schedules, leave entitlements or wages. These remain operational requests subject to human workload and blocker review, not automatic excuses or findings of misconduct.

New requests are allowed through signed version 45, decisions/withdrawals through version 47, leaving capacity for work submission and independent completion within the 50-version record bound. Work can continue while a request is pending. Near the bound, terminal verification/cancellation still closes the pending request; records are read-only after completion/cancellation. This bounded workflow does not provide scheduled reminders, emergency escalation, indefinite task recycling or automatic HR/payroll decisions.

## Employee workload oversight

Scheduling, tenant administration, clinical directors and RN field supervisors can review the operational employee-workload panel. Other care roles receive no organization-wide workload aggregate. This report groups unfinished follow-up tasks by owner and shows open, blocked, overdue, submitted-for-review, pending-deadline-request and waiting-on-prerequisite counts, plus the earliest unfinished deadline. Completed and cancelled tasks are excluded. The report does not join client names, clinical charts, care notes or task-evidence text. It does not establish employee fault, hours worked, pay entitlement or a disciplinary finding.

To use it in the app:

1. Search an employee email or account ID in the workload panel, or browse its 25-owner pages. Search is a case-insensitive literal match, limited to 100 characters; `%`, `_` and `!` are ordinary text, not wildcards. Empty search shows all authorized owners with unfinished work. Owners sort by email then account ID, rather than a performance ranking.
2. Select **View employee tasks**. The follow-up panel shows the selected owner explicitly. Select blocked, past-target, submitted-review or deadline-request work to examine the actual signed evidence. Owner and status filtering happen before task pagination. The follow-up counts describe that owner’s unfinished tasks across statuses; the workload panel’s totals describe its employee search independently.
3. Address the blocker using the existing evidence, independent deadline-review, reassignment or completion-review workflow. Approving more time preserves the blocked/in-progress/submitted status. Only the owner resumes work; only another operations person verifies completion. Selecting **Show all authorized employees** clears the owner filter and restores the all-status queue.

Inactive accounts and accounts whose role no longer permits care tasks remain in the report while they own unfinished work, with a reassignment warning. Their old evidence remains intact. An active, authorized operations employee must arrange appropriate replacement ownership; the report grants no care authority. Owners beyond the current 200-person staff picker can be found in workload search/pagination and their existing tasks opened. The assignment/owner pickers themselves remain bounded; this is not a complete organization-wide staff-directory editor.

The API uses the existing care snapshot with `workloadOffset`, `workloadQuery` and optional `followupOwner`; `followupView=blocked` adds the blocker queue. Support staff may filter only to themselves and cannot obtain another employee’s metadata or organizational summaries. Foreign-tenant owner IDs are hidden. All database access and filtering remain on the API; the UI presents returned records and counts. Counts are a transactional read snapshot, updated on refresh or the next action, with no scheduled reminder or live push service. A partial unfinished-task index is supplied; large production workloads still require capacity and query-plan validation.

## Operational prerequisites and waiting work

When creating a follow-up, operations may select up to five existing, non-cancelled tasks from that same care visit. Selection is optional. The picker lists the latest 100 eligible task records and shows a truncation warning when older records are omitted. The API still checks every supplied task ID, tenant and source visit; text and UUID identities are supported. Task references are displayed in the queue so operators can identify the selected record. No predecessor instructions, notes or event history are copied into another owner’s task.

A task owner cannot start or submit dependent operational work until all prerequisites have been independently verified as completed, or validly released. A submitted predecessor is not completed. Independent completion verification checks the dependencies again and also checks the actual source workflow for that task category. Prerequisite completion is historical task evidence; it does not prove that a clinical plan or qualification remains current. Existing care, consent, qualification and source-outcome checks remain separate. These are operational follow-up gates, not a new clinical treatment-order system or a replacement for physical-visit start checks.

Cancelling a prerequisite leaves its dependents waiting. Another operations person may arrange replacement work through normal task workflows, cancel unneeded dependent work, or record a justified exception. A release requires a reason and explicit confirmation from an operations person who owns neither the dependent task nor the prerequisite. The release does not complete either task, alter the original deadline, resume blocked work, clear an extension request or approve clinical care/payroll. It records the predecessor’s contemporaneous owner/status, reviewer and time. Release decisions and links cannot be edited or deleted. A later owner change is checked before any idempotent replay; old success does not restore authority.

The task panel offers **Waiting on prerequisites** (`followupView=waiting`) with server filtering before pagination. Employee workload also counts waiting tasks. A task can be both overdue and waiting, or explicitly blocked and waiting; these are separate facts, not an automatic finding of fault. When the predecessor is completed, refresh/action reload derives readiness without silently changing the dependent’s status, version, deadline or signed evidence. The owner still resumes or submits their own work.

Links can only be created with a new task and must point to existing records. The API offers no post-creation rewiring, so it cannot introduce dependency cycles. Composite database keys prevent cross-visit links. All follow-up mutations lock the source visit/case before the task, and then coordinate staff locks; this order also covers prerequisite creation and release. External writers must use the same API/lock protocol. Releases are permitted through task version 47, leaving room for a final submission and independent decision within the 50-version bound. If the record bound prevents further correction, operations can cancel the old task and create replacement work with preserved history. This bundle does not provide cross-client project graphs, automatic recurring duties or scheduled dependency reminders.

## Find staff for care operations

Operations use the shared staff-search panel above clearance and staffing. Enter part of an email or account ID and select **Search staff**. The API searches active, supported-role employees in the current tenant before returning up to 200 matches. Search ignores letter case and treats SQL wildcard characters as ordinary text. Empty search restores the initial roster; narrow a search when matches exceed the bound.

Results feed care assignment, clearance, availability/leave and eligible follow-up owner selectors, including task reassignment. Follow-up owners remain limited to current active care-team members and permitted operations staff. Active care-team options are retained even when they do not match the search, including team members beyond the first 200 staff. A selected staffing-history employee remains available when a different search is entered. Search grants no qualification, care, task or leave-approval authority; all mutations recheck the current account, role, tenant and applicable workflow.

Assignment and clearance selections remain available while searching for another team member. Form drafts are restored after search/paging; a restored selector value must exist among its current options. A superseded search response cannot restore older drafts over a later response. These are display conveniences, with server-side checks remaining authoritative.

## Find an unassigned appointment

Within assignment, enter part of a client name or appointment ID and select **Search appointments**, or use **Previous** / **Next** to browse 25-record pages. Search is literal and case-insensitive, runs before pagination and returns the matching total. A new search starts from the first page. Paging/search preserves staff selections and assignment evidence and clears the previous appointment choice so the coordinator explicitly selects a currently displayed appointment.

Only operations can retrieve these appointment labels. Active client accounts, tenant boundaries, eligible appointment status and absence of an existing care case are checked on the API. Cancelled, rejected, completed and already-assigned appointments are excluded. Stable appointment-start/ID ordering avoids duplicate entries between unchanged pages. Concurrent source changes can alter later page contents; creating an assignment still rechecks the source and current permissions atomically. Search results expose only appointment ID, start time and client name, not clinical chart text. The existing source-assignment transaction remains authoritative.

No new table migration is required. New controls, translations, query fields and response metadata are registered through `scripts/register-care-governance.py`; the dashboard uses existing theme tokens and UI primitives. The `visitPickerPolicy` defines page size, query bound and operations scope in governance. The API accepts `rosterQuery`, `visitQuery` and `visitOffset` under its existing authenticated, rate-limited care snapshot route. Invalid, duplicate, control-character and out-of-bound query values are rejected.

## Find recurring-visit source appointments

Operations can search the recurring-source selector by a literal, case-insensitive client-name fragment or source appointment ID, and browse independent 25-record pages. A new search returns to the first source page; source paging does not move the recurring-series history page. Search results require the same tenant, active client account, active service and nonblank required skills. Cancelled/rejected source visits are excluded. Completed and already-assigned appointments remain eligible as source templates, because creating future visits copies scheduling details without copying care plans, staff approval or completion.

Searching or paging sources clears the old source choice and hides the prior preview while preserving other schedule-form entries. The operator selects a displayed source and obtains a fresh preview through the existing authenticated, conflict-checked scheduling API. No existing visit, clinical plan, worker assignment or payroll record is modified by browsing.

The existing snapshot accepts `sourceQuery` (at most 100 characters) and `sourceOffset` (bounded by the existing offset policy). Source eligibility, query bounds, page size, controls and EN/FR/ES wording are governance-backed. Ten focused text/UUID picker checks passed, as did expanded API checks and the real recurring-source search/preview/create/cancel browser workflow. CI now includes the roster and visit-picker regression scripts alongside the care, workspace and auth-client checks.
