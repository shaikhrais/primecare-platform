# PSW Getting started: training replacement

Status: design reference and integration requirements only. Do not expose this file as a production screen or mark it verified.

- Existing web surface: PSW workspace, Getting started, `/psw#guide`, `psw_personal_guide`, `PSW-T08`, source-mapped journey `care.psw.personal.guide`. Verify the exact current records and scope through the pinned governance adapter. The same renderer serves HSW and admin preview: preserve their current guide and do not modify general Academy, Administrator Training, or the Help reader.
- Structure: start wizard (choose Desktop, Tablet, or Mobile → review device media → Day 1), one practice activity per day, every-shift checklist, collapsed task-code library. Start with the illustrated Day 1 and Availability lessons as the first increment. Adapt the reference into registered, shared PrimeCare components and theme tokens; do not mount the standalone file or assign access from UI flags.
- Before runtime changes: read back existing screen, role, section, action, resource and API bindings. Submit missing wizard/device/media controls and English, French and Spanish resource keys through the established governance process. Keep screen access on the server; do not hardcode new IDs, register an invented endpoint, or expand any worker's clinical authority.
- Storage: keep approved synthetic lesson images, captions, transcripts and clips in private object storage behind the already approved tenant/role-scoped file/media contract, after confirming the exact binding. Store the media object reference, version, locale, device class, size, and approved publication state with the training record; do not put binary media or credentials in PostgreSQL, the public repository, or the UI. Do not use CI artifacts as the delivery backend. If no approved media binding exists, keep downloads unavailable until it is registered.
- Media gaps: current historical QA has a real 1440 CSS-pixel desktop capture and 320 CSS-pixel mobile captures plus one mobile sign-in/availability clip. Tablet 768 CSS-pixel tests did not retain a tablet recording. No approved course-media set exists yet. Use the synthetic fixture only, never patient information, and label the actual tested device/viewport.
- Device downloads: choose the explicit approved version. Any app-managed cache must separate accounts and tenants; clear only app-managed lesson media on the current device. Clearing training downloads is not Clear demo data, and cannot erase files manually exported to system Downloads.
- Missing task reports: reuse the existing PSW team request queue only after adding and registering a specific type and task reference. Keep expected/observed behavior free of patient data; check tenant/owner on both submission and lookup, handle retries, and show the tracked result. Do not imply the current queue already has that type.
- Required checks in GitHub Actions: PSW/HSW/nonworker scope, device selection and restart, keyboard and screen reader behavior, translated views, unavailable media states, safe playback/download/cache clearing, and ticket isolation if introduced. Use only a test-only workflow and synthetic records. Don't dispatch a workflow that publishes to production just to get tests. Operations/training and appropriate clinical reviewers must approve lesson content before publication.

See [the offline design reference](psw-training-preview.html) for compact content and the interaction model.


## Evidence and missing-work queue

For every task and supported device, attach a source link at an exact commit, the latest result for the task on that commit, a sanitized screenshot and a sanitized video. Show code state (not found, source found/unverified, demonstrated, blocked), screenshot state (missing, historical, reviewed), and video state independently. Prefer an exact route and simulated PSW actor; confirm persisted results after reload where applicable. Retain links to the CI run, approved media version, language, viewport, review and any invalidation by later changes.

When an item is missing or stale, prepare a request with task code, device, requested code or evidence and acceptance criteria. The offline reference only drafts text; it neither sends nor creates tickets. Use a versioned, tenant- and owner-scoped request type when a governed workflow is implemented, then read back its ID, status and resolution.
