# PrimeCare central control and inheritance

## Implemented Worker hierarchy

`BaseWorker<Environment>` owns the request lifecycle: preflight, dispatch and
error handling. `ServiceWorker` and `GatewayWorker` inherit it and supply their
host behaviour. Worker exports remain plain objects with a bound fetch closure,
so destructured host calls work. Instances store no request, actor, tenant or
mutable policy state.

All twelve service configurations generated by
`scripts/generate-cloudflare-worker-config.mjs` point to `service.ts`. Thus one
shared service class controls their lifecycle. The gateway shares the same base.
`business-modules.ts` is the immutable, ordered list of seven domain handlers.
Legacy handling and auth/source limiting stay ahead of that list. Each domain
handler retains its existing verified identity, ownership, tenant and grant
checks. This refactor adds no workflow authority and completes zero new APIs.

| Change required | Central location |
| --- | --- |
| Shared request lifecycle | cloudflare/workers/src/core/base-worker.ts |
| Service dispatch, service preflight and safe failures | cloudflare/workers/src/service.ts |
| Domain registration and precedence | cloudflare/workers/src/business-modules.ts |
| Gateway paths and service bindings | cloudflare/workers/src/gateway.ts |
| Authentication and verified request identity | cloudflare/workers/src/auth.ts |
| Authentication policy values | Existing account-policy/auth-security-policy/auth-source-policy JSON files |
| Governed UI parent and shell | packages/flutter_core/lib/models/screen.dart |
| UI networking and resilience | Existing flutter_core ApiClient and Result facilities |

A base class controls shared behaviour; typed policy files control parameters.
An HTTP lifecycle parent cannot replace domain-specific transaction and authority
checks. Never store request identity in a shared singleton or accept client policy.
Dart classes cannot run inside TypeScript Workers: keep equivalent contracts and
separate runtime adapters.

## Migration sequence for the rest of the repository

### Web session transport

`websites/typescript/src/infrastructure/http/base-session-client.ts` contains
`BaseSessionClient`. `CareClient` and `GrowthClient` inherit its session checks,
JSON transport and per-instance idempotency retry lifecycle. Concrete clients
retain their governed endpoints, public request signatures and error policies.
Care keeps typed HTTP errors; growth keeps its unauthorized redirect and uncertain
delivery errors. The base normalizes non-object JSON error bodies so a null or
primitive response cannot replace the domain failure with a property-access error.
Growth PDF validation remains in its adapter and uses the inherited
session check. No account or tenant is stored globally by the base class.

`scripts/test-session-client-inheritance.mjs` verifies both inheritance links,
request payloads, retry reuse and reset, instance isolation, account changes before
and after requests, domain error differences and PDF validation. Care acceptance
CI includes this suite. This extraction creates no screens, APIs or permissions.

This is a partial architecture migration. CareRepository remains a concrete class;
care domain workflow handlers and web presentation functions have not all been
converted to class hierarchies. Territory, tenant operations and other clients
still have different transport contracts and need separate compatibility review.
The existing Dart parents and Worker BaseWorker hierarchy remain authoritative
for their runtimes; Dart base classes cannot be inherited by TypeScript code.

### Remaining migration sequence

This PR migrates the thirteen Worker entry points through two concrete classes.
It does not migrate every Dart service, Flutter screen or domain handler into a
new class hierarchy. The shared governed UI parent already exists and should be
reused. Legacy Dart routes include placeholder success bodies; inheritance alone
cannot turn them into complete workflows.

1. Inventory active deployment manifests, exact callers and handler ownership.
   Current top-level pubspec inventory: 9 apps, 13 services and 3 packages;
   this excludes archived projects and is separate from the 12 Worker services.
2. Keep Worker lifecycle subclasses and domain registry as the shared backend root.
3. Extract repeated, tested domain behaviour into typed base use cases only after
   resource scope, authorization, transaction and error contracts are established.
4. Connect each Flutter feature to existing governed screen parents, Riverpod
   controllers and typed SDKs. Do not replace the flutter_core package wholesale.
5. Keep repository adapters responsible for tenant-scoped queries and transactions;
   do not generate a global CRUD parent with unrestricted table/field access.
6. Migrate active Dart services in coherent packages, preserving routes and payloads.
7. Test the proposed head and CI before merging; deployment remains a release step.

## Verification and evidence

`python3 scripts/check-skeleton-structure.py` checks the current registered
skeleton without Git history: 1,161 controller inheritance links, eight app
roots, 13 organized service hosts, two Worker subclasses and two web session
clients. It rejects controllers that override the shared lifecycle, app roots
that rebuild MaterialApp locally and service entrypoints that retain host classes.
Central inheritance CI runs this in addition to the historical parity checks.
The structural check does not replace compilation, workflow tests or historical
behavior comparisons, and does not claim that every repository feature uses a
base class.

The base lifecycle tests cover preflight termination, asynchronous hook ordering,
error delegation, parallel request isolation and detached fetch calls. Twelve
service cases verify root responses, allowed preflights and rejected origins
without database access. Existing route/auth/blocker tests exercise compatibility.

The method-capture blocker source fingerprints include the extracted base,
service and registry in addition to the gateway and existing authority evidence.
Previous historical evidence files remain historical; fingerprints are not rewritten
to imply older test runs exercised this refactor. No grants or governance records
are changed by this PR.
