# Governance route access

The governance router now requests `/v1/governance/workspace` before entering native or dynamic business routes. Only an exact route in the authenticated response `screens` projection can authorize navigation, and the local presentation registration must also exist. The response user and role must match the captured session; token, tenant, user and role changes invalidate pending decisions. Navigation rechecks grants rather than caching them. The API retains responsibility for server session, tenant and business-record authorization.

Login uses the server landing only when that exact route is both visible and locally registered. Suffix matches, role-name guesses, arbitrary dashboards, inventory entries and placeholder fallback no longer authorize navigation. Errors, missing identity, non-200 responses and malformed or duplicate route projections deny access through the existing auth-error route. Existing shared public auth and authenticated account/consent routes keep their existing handling.

The six unmapped native business routes and fallback remain denied until authoritative mappings exist. No aliases, roles or production grants are created. This guard does not certify the production freshness of the server catalog or implementation of the underlying business tasks.

Validation: `governance_route_access_test.dart` exercises exact grants, malformed/foreign identities, inventory exclusion, similar CEO paths, revocation on subsequent navigation and stale-session responses. `governance_route_guard_test.dart` exercises the actual router redirect across every native route, non-200 responses, valid landing and session replacement. These Flutter tests must pass on the published head before this change is accepted. Native widget presentation tests that mount builders directly remain presentation-only evidence.

The route-site digest update covers the changed router container, not a grant or production-readiness approval. Full staging, API authorization, accessibility, localization and workflow acceptance remain separate release gates.

The governance router also mounts exact routes from the existing generated workspace catalog that are absent from the legacy registry. Existing native, auth, account and registry routes keep their builders; no aliases are inferred. Each supplemental route uses `GovernedWorkspaceScreen` inside the existing managed shell and still requires a fresh exact server grant. This fixes missing canonical landings (including the RMT dashboard) and canonical CEO business-page navigation; the six unsupported legacy native paths remain denied. Shared workspace pages retain their existing incomplete-business-task indicators. Catalog connectivity is not screen completion. The actual-router test initializes the production registry and checks permitted/denied RMT landing and three CEO business routes, exact renderer binding and uniqueness.

Registry startup no longer fabricates completed lifecycle status, a 100% test rate, accessibility/security/PHI approvals, verification hashes or a QA approver. It preserves the recorded source evidence and performs only the existing empty-route normalization. `governance_registry_evidence_test.dart` compares every registered metadata record to its source and preserves unrelated partial test evidence. This corrects local display metadata only; no production workflow verification is written.

Completely blank legacy records (empty title, feature, route and role list) are retained in `CoreGovernanceRegistry.unresolvedMetadata` instead of being given executable `/reconciled/...` routes or administrator roles. Existing stale manufactured entries for those IDs are removed from the executable registry. The source inventory is retained; the readiness artifact includes both executable and unresolved records and the original record count. A new release assertion requires the unresolved inventory to be empty, while the zero-critical, 80% health and 50% readiness gates remain unchanged. This quarantine is containment, not completion of those records or business workflows.

Known invalid executable placeholders now have an exact-match retirement rule: the nine inspected LABELS IDs must match the original blank metadata, icon and all serialized source fields. Their full original records remain in a read-only retired inventory and in the readiness artifact; total inventory counts include them. They have no widget binding or workspace catalog identity. This is dead executable-metadata cleanup, not a screen acceptance, production database deletion, grant change or retirement of label/resource content. Changed evidence or unknown blank IDs are not covered by this rule and remain unresolved, with the release gate still enforced. Real health/readiness thresholds are unchanged and may continue to fail.
