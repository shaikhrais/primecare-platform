# Six-month business plans in the PrimeCare project

The native portal route `/business-plans` and governance endpoint `/v1/governance/growth/cycles` use the platform PostgreSQL database and current account sessions. This is a source integration of the separate execution-centre template engine, not an iframe or external login. The existing execution-centre data remains unchanged; its owner-private plan records are not copied into tenant accounts.

Fourteen version-one templates cover master/tenant startup, growth, maintenance, client relationships, cost efficiency, lean operations and recovery. Each cycle is 180 calendar days with an owner-confirmed start, zero initial achievements, unknown readiness and HOLD. The platform stores a template snapshot and version. A manager supplies a local baseline/capacity assessment, can adapt unmeasured targets, chooses dates and assigns active accounts from the selected organization. Template targets remain assumptions, not research-validated business forecasts.

Code/platform/central admins can select existing active organizations. CEOs, owners and tenant admins manage their own tenant. Marketing/local marketing and growth caller, Google, Meta, SEO, offline and coordinator roles see assigned tasks and linked targets only. They cannot approve their own work or edit goals, readiness, scope or templates. Supporting clinical/provider/patient roles receive no new business-data access. Global template publication is reserved for code/platform admins; other managers submit proposals. Changing roles does not bypass current session and active-account checks.

Loop: choose a template → verify baseline and capacity → adapt local targets → assign named people → set date → readiness and launch decision → staff evidence submission → different manager acceptance → measured business results → weekly gap review → 7/14/21/30-day recovery with four detailed corrective tasks → evidence review → approved future template version → fresh next cycle with prior outcomes as baseline only. Existing plans retain their version, dates and evidence. No automatic dismissal, unsafe staffing cut, fabricated achievement or guaranteed business outcome.

Every mutation is tenant-scoped and transactional with an independent audit entry, session-bound actor attribution, optimistic plan version and request-idempotency protection. Completion requires evidence and accepted dependencies. A different manager must review the submitter's work. Plan A requires confirmed baseline, a schedule, working readiness checks and named task assignments. Recovery closure requires the four corrective tasks to be accepted.

The migration inserts a durable role-targeted announcement available to current and future eligible accounts, and assignment/review operations create individual in-app notices with per-user read receipts. This does not send external email, SMS or calls. New tenants can choose their first template; no plan is started automatically. All eligible roles find the module in the existing administration, growth or account/workspace navigation.

Limits: manager lists are bounded at 100 recent plans, 100 lessons and 100 notices; global organization selectors and active team lists at 300. Audit detail is bounded to 100 recent entries per plan. Template catalog keeps five latest versions per stage in the UI; existing snapshots remain available in saved plans. Histories are retained in PostgreSQL; a 1.5MB saved-plan cap prompts a successor cycle. Evidence references must contain no patient records. No external scheduled reminder job is introduced; overdue and gap indicators recalculate on page load/refresh. Managers must establish their weekly review routine.

Validation: `scripts/test-business-plan-cycles.mjs` exercises the native PostgreSQL schema, template instantiation, tenant isolation, assigned-only projection, manager acceptance, readiness gating, recovery, immutable versions, next-cycle baselines, audit and notices. `scripts/preview-business-plan-project.mjs` runs the real API handler against a synthetic embedded PostgreSQL fixture to verify bearer-session rules, role denial, scope boundaries, idempotency, suspension and the production UI bundle; it provides an optional browser preview. No synthetic fixtures are seeded to production. The production workflow applies an additive migration, verifies all 14 immutable templates, preserves live Worker bindings, publishes every portal and confirms live unauthenticated requests are rejected. A successful release proves deployment and these checks; it does not prove future business results or real-user adoption.
